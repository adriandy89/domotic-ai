## 2. Integración Alexa

**Implementado y correcto**: servidor OAuth2 propio (códigos de un uso, hash SHA-256,
`timingSafeEqual`, `redirect_uri` exacto con allowlist de hosts de Amazon), Lambda proxy,
Discovery (+ escenas IR), Power/Brightness/Color/ColorTemperature/Thermostat/Lock,
ReportState, auditoría `source='alexa'`, UI de ajustes en/es/fr, guía de despliegue.

Arreglado (con tests unitarios + e2e):

- ✅ **Fallar cerrado**: un nombre de directiva desconocido en Power/Lock caía a "off" /
  **"desbloquear"**. Ahora `INVALID_DIRECTIVE` (`directive-to-command.ts`).
- ✅ **Aislamiento entre organizaciones**: un cliente OAuth de la org A podía vincular
  usuarios de la org B (phishing con la skill de A). Ahora authorize/decision exigen
  misma organización y el token se rechaza si el cliente está desactivado o es de otra
  org (`alexa-oauth.controller.ts`, `alexa-token.service.ts`).
- ✅ **Desactivar el cliente corta el acceso al instante** (antes duraba hasta 1 h).
- ✅ **Clickjacking/caché** en la página de consentimiento: `X-Frame-Options: DENY`,
  `frame-ancestors 'none'`, `no-store`.
- ✅ **Refresh tokens conforme a Amazon**: el token rotado sigue válido 60 s (reintentos
  de Alexa no desvinculan al usuario); desvincular/replay de código/borrar cliente
  BORRAN las filas (no reutilizables); el refresh exige usuario activo y cliente de su
  organización; se limpian los rotados antiguos (antes crecían sin fin).
- ✅ Parámetros repetidos / Basic mal codificado → 400/401 en vez de 500.
- ✅ Protocolo: errores de AcceptGrant con namespace `Alexa.Authorization` (servicio,
  middleware y Lambda); Discovery
  con token inválido devuelve lista vacía; `description` ≤ 128; solo se reportan modos
  de termostato válidos para Alexa.
- ✅ Lambda: respuestas no-evento → `ErrorResponse`; documentado timeout de 8 s.

## 3. IA (Mastra)

Arquitectura: web/Telegram → API `POST /ai/chat` → NATS `ai.generate` → ai-service
(una instancia Mastra por organización, caché 15 min, PostgresStore + PgVector,
20 tools de `libs/ai-tools`). Modelos por organización (openai/google/openrouter).
MCP server en la API y puente xiaozhi en `integrations`.

- ✅ **Fuga de conexiones Postgres**: al expulsar/invalidar una instancia no se cerraba
  nada (`(mastra as any).stores` no existe en Mastra 1.x) → 2 pools filtrados por
  expulsión. Ahora la factoría cierra store + vector (`dispose()`), SOLO cuando termina
  la última petición en curso de esa organización (cambiar la config de IA ya no corta
  respuestas a medias), y dos primeras peticiones concurrentes comparten instancia.
- 📋 **Nombres de tools**: el modelo ve las claves (`sensorDataTool`…) pero el prompt
  y el MCP hablan de `get-devices-list`, `send-device-command`… Registrar por `tool.id`.
- 📋 Reglas creadas/borradas por la IA no avisan al edge (`EdgeSyncNotifier`).
- 📋 "Borrar chat" no borra memoria; web y Telegram comparten hilo (`user.id`).
- 📋 Se devuelve `error.message` crudo al usuario; timeout NATS 60 s.
- ⚠️ La API key del proveedor IA se devuelve completa al navegador y se guarda sin cifrar.
- 📋 Sin streaming (axios espera la respuesta completa); sin Markdown; textos sin i18n.
- 📋 Código muerto: `processors/*`, listas de modelos duplicadas, `getStats()`.
- 📋 Paquetes instalados sin uso: `@mastra/rag`, `@mastra/ai-sdk`, `@mastra/loggers`,
  `mastra` (CLI, dependencia de producción pesada), `ai` (solo en código muerto).
- 📋 Token MCP aceptado en la URL (`?token=`) → acaba en logs.

## 4. Plataforma / infraestructura

- ✅ **`init` hacía `FLUSHALL`** en cada arranque: borraba las sesiones (logout de todos)
  y las colas BullMQ (schedules, reglas diferidas, watchdog) hasta reiniciar
  rules-engine. Ahora `flushAllExcept(['sess:', 'user-session:', 'bull:'])` (verificado
  en local; `user-session:` mantiene "cerrar las demás sesiones").
- ⚠️ **Sesiones nunca revalidadas** (preexistente, ahora más visible): `deserializeUser`
  devuelve la copia del usuario guardada al hacer login; desactivar, degradar o borrar
  un usuario no corta sus sesiones (antes el FLUSHALL de cada despliegue lo hacía por
  accidente). Arreglo: recargar `is_active/role/organization_id` de BD (con caché
  corta) y destruir `sess:*` al desactivar/borrar.
- ✅ **CORS + CSRF**: CORS reflejaba cualquier origen con credenciales (+ cookie
  `SameSite=None` en prod) y, aunque se restrinja, un `<form method=POST>` de otra web
  seguía llegando al handler con la cookie (p.ej. `POST /ai/chat` "abre la cerradura").
  Nueva variable `CORS_ORIGINS`: restringe CORS **y** bloquea escrituras con `Origin`
  ajeno (`security/cross-site-guard.ts`). ⚠️ **Configúrala en producción** (sin ella
  nada cambia y se avisa en el log). Valorar además `SameSite=Lax` si web y API son el
  mismo sitio (`.domotic-ai.com`).
- ⚠️ **`stack-docker/docker-compose.yml` publica en 0.0.0.0** Postgres 5433
  (postgres/postgres), Redis 6379 (contraseña en git) y NATS 4222. Docker se salta UFW.
  Si ese compose corre en el servidor, comprobar desde fuera y publicar en `127.0.0.1`.
- 📋 `POST /devices/command/send` acota solo por organización, no por pertenencia a la
  casa (regla 4 de CLAUDE.md); decidir si MANAGER es global a la org.
- ⚠️ **TimescaleDB PG18 en `stack-docker`**: la imagen `latest-pg18` guarda datos en
  `/var/lib/postgresql/18/docker`, pero el compose monta el volumen en
  `/var/lib/postgresql/data`. Con un volumen vacío, PG18 inicializa los datos **fuera
  del volumen con nombre** (en un volumen anónimo). **En el servidor: comprueba

  contenedor. Fijar además la versión de la imagen.

- 📋 `schema.prisma` ≠ migraciones incluso en BD nueva (32 sentencias: nombres pk/fk,
